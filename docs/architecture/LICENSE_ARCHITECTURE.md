# Licence Architecture

## 1. Components (Part 18.1 decision)

| Component | Distribution | Source |
| --- | --- | --- |
| Main application (includes the **dedicated activation component**) | Public installer | `src/main/`, `src/core/licensing.ts`, `src/renderer/pages/Activation.tsx` |
| Owner-only licence generator | Private, owner-controlled artifact; CI workflow artifact only | `apps/license-generator/` |
| Customer activation as a separate EXE | **Not built** — documented decision | — |

The prompt permits a "dedicated activation component" instead of a second executable.
A separate EXE would duplicate the verification code, require another signed binary, and
complicate offline file hand-off. A dedicated first-run module inside the main app uses
exactly the same `verifyLicense()` function as the generator's self-check, so the two
cannot drift. This satisfies Part 18.1 while reducing attack surface.

## 2. Cryptography

Ed25519 (`crypto.generateKeyPairSync('ed25519')`, `sign(null, payload, privateKey)`,
`verify(null, payload, publicKey, signature)`) per Node's crypto API
[2](https://nodejs.org/download/release/latest-v24.x/docs/api/crypto.html). The public
key is embedded as a PEM constant in `src/core/licensing.ts` and compiled into the main
app. The private key is generated by the owner into a path excluded by `.gitignore`; it
is never in git, never in a build log, never in an installer, and never in a public
release.

Canonical signing input: JSON with keys in a fixed order (`{ "alg":"Ed25519", "v":1,
"productId":"MERQO-POS", "licenseId":..., "businessName":..., "businessInfo":...,
"licenseType":"LIFETIME", "issuedAt":..., "issuer":"MERQO", "deviceFingerprint":...,
"policy": {...} }`), UTF-8 encoded, signed as bytes. Verification recomputes the same
canonical bytes; a reordered or modified field breaks the signature.

## 3. Licence file format

```json
{
  "format": "MERQO-LICENSE-1",
  "payload": { "...": "..." },
  "signature": "<base64 Ed25519 signature>"
}
```

`licenseId` is 16 random bytes in base32, prefixed `MQ-`, and uniqueness is enforced in
the generator's private local record database. Business identity is inside `payload`,
so an attacker cannot just type a matching business name.

## 4. Device binding

The activation component computes a fingerprint from hashed Windows identifiers:

| Component | Windows source | Stability |
| --- | --- | --- |
| machine | `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` | survives disk swap, changes on reinstall |
| disk | `wmic diskdrive get SerialNumber` / PowerShell CIM | survives reinstall, changes on disk replacement |
| cpu | `wmic cpu get ProcessorId` | stable, low entropy |
| user SID | `whoami /user` | changes with Windows account |

Each component is SHA-256 hashed separately; the licence stores the list. Verification
requires a **majority match** (≥ 2 of 4 on first activation, ≥ 2 thereafter) so a single
hardware change or Windows reinstall on the same machine does not invalidate a lifetime
licence. A transfer requires the owner to issue a replacement licence bound to the new
approved fingerprint; the old licence ID is recorded as superseded in the owner's private
records. This is an honest offline policy, not a claim of unbreakable copy protection.

## 5. Offline activation flow

1. First launch reads `<userData>/license/activation.json` (absent → locked).
2. Activation screen asks for the customer's `.merqolic` file (or pasted activation data).
3. `verifyLicense()` checks format, signature, product, licence ID, business identity,
   integrity, device binding and policy.
4. On success, activation is stored in the `license_info` table plus a signed activation
   record file; audit row written; app unlocks the setup wizard.
5. On failure, a specific safe error is shown and no business data is created.

No internet call is made at any point. There is no expiry field, no renewal and no
periodic verification.

## 6. Generator security rules

* Run only on the owner's machine; private key file permissions 0600.
* Output directory excluded from git; EXE built by CI as a protected artifact only.
* Never attach the generator or private key to a public GitHub release.
* Generator records (licence ID, business, device fingerprint, issue date, superseded ID)
  stay in the owner's private local store, outside the repository.
* `scripts/build/verify-no-secrets.mjs` fails any build containing a private key.

## 7. Recovery/transfer

Owner verifies the customer's request out of band, collects the new device fingerprint
(a small offline diagnostic file produced by the activation screen), issues a replacement
licence with a new `licenseId` and `supersedes` field, and the customer imports it. The
app increments `recovery_count` and writes an audit row. No online check occurs.
